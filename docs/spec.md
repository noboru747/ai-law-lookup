# 消費糾紛法規查詢助理 — 專案規格

> **修訂說明**：本文件以原始規格為底稿。Phase 0／Phase 1 完成後所做的修訂，皆以「修訂（Phase 0）」「修訂（Phase 1）」標示，原文保留以利對照。修訂依據見 [phase0-source-verification.md](phase0-source-verification.md)、[ADR 0005](decisions/0005-snapshot-date.md)、[ADR 0006](decisions/0006-provenance-over-amendment-dates.md)。

作品集專案。目的是展示對 DB、RAG 與 AI 應用邊界的理解，不是做一個完整的法律產品。 系統定位為「法規資訊查詢」，不提供法律意見、不對個案下結論。

## 1. 專案目標

針對一般民眾常見的消費糾紛，透過問診引導，找出相關的官方條文，並整理成附有引用依據的回答。

展示重點：

- 範圍控制：清楚說明做什麼、刻意不做什麼，以及為什麼
- 分層架構：確定性流程與模型生成的分工
- 可追溯性：每個回答都能回溯到官方原文
- 可用性：後端離線時能自動降級

## 2. 範圍

### 2.1 收錄（內容層）

| 類別 | 內容 | 備註 |
|---|---|---|
| 核心 | 消費者保護法：通訊交易／訪問交易解除權、定型化契約一般規定、申訴與調解流程 | 必收 |
| 核心 | 通訊交易解除權合理例外情事適用準則 | 例外商品清單 |
| 行業別 | 2～3 個高頻行業的「定型化契約應記載及不得記載事項」，候選：禮券、健身中心 | 先選 2 個 |

| 類別 | 官方正式名稱 | 來源 | 備註 |

| 核心 | 消費者保護法（J0170001） | 全國法規資料庫開放資料 | 必收 |
| 核心 | 消費者保護法施行細則（J0170002） | 全國法規資料庫開放資料 | **新增**：第 12～15 條（定型化契約）、第 17、18 條（解除權） |
| 核心 | 消費爭議調解辦法（J0170008） | 全國法規資料庫開放資料 | **新增**：支撐「消費申訴流程」葉節點 |
| 核心 | 通訊交易解除權合理例外情事適用準則（J0170012） | 全國法規資料庫開放資料 | 名稱與候選一致 |

行業別已定案為禮券與健身中心。

### 2.2 只辨識、不回答（目錄層）

- 其他行業的應記載事項
- 周邊法規：民法買賣瑕疵擔保、公平交易法、食品安全衛生管理法、商品標示法等
- 回覆方式：辨識出可能相關的法規名稱 → 說明不在收錄範圍 → 轉介

### 2.3 刻意排除（寫進 README 的設計取捨）

| 排除項目 | 理由 |
|---|---|
| 刑法 | 高風險，且不屬於消費糾紛 |
| 勞基法 | 高度依賴主管機關解釋、涉及計算、行政機關與法院見解分歧 |
| 稅務 | 屬於計算型問題，需要年度參數表與計算引擎，是另一套系統 |
| 交通 | 原本的候選領域，為了收斂 MVP 範圍而暫緩 |
| 判決書 | 量大、格式雜亂、見解分歧 |
| 函釋全集 | 範圍會爆炸；必要時以主管機關官方說明頁補充 |
| 緊急應對（失火、自傷等） | 不在設計目標內，統一使用非法律模板回覆 |

## 3. 系統架構

```
使用者輸入
   │
   ▼
[1] 範圍判斷 ── 非法律問題 ──► 固定模板：「本系統僅提供法律資訊查詢」
   │
   ▼
[2] 問診樹（固定流程，JSON/YAML 定義）
   │   ├─ 情境分類（以生活情境分類，不以法律名稱分類）
   │   ├─ 「其他」→ 自由輸入 → 由模型重新導向正確分支
   │   └─ 葉節點：一次表單補齊必要欄位（只問會讓答案分岔的欄位）
   │
   ├─ 葉節點 type = out_of_scope ──► 目錄層模板 + 轉介
   │
   ▼
[3] 篩選層：依節點的 law_scope 限定檢索範圍（確定性 metadata 過濾）
   │
   ▼
[4] 檢索層：條文檢索 + 引用關係展開
   │
   ▼
[5] 生成層（Ollama，可拔除）：條文要件 × 使用者事實 → 附引用的回答
   │
   ▼
輸出：回答 + 條號與原文 + 轉介資源
```

### 3.1 核心原則

- 需要精確的地方，用確定性的程式處理；需要語意理解的地方，才交給模型。
- **沒有檢索到範圍內的條文，就不呼叫模型自由生成。**範圍外一律使用模板回覆。
- 分支由程式決定，文字由模型生成；模型不負責下結論。
- 每個回答都必須附上條號和原文；找不到依據時明確拒答。
- 涉及見解分歧或「取決於契約內容」時，要明確標示。

### 3.2 部署（方案 C：靜態前端 + 可降級）

| 元件 | 位置 | 說明 |
|---|---|---|
| 前端 | Cloudflare Pages | 靜態網站 |
| 問診樹 | 前端（JSON） | 在瀏覽器中執行 |
| 檢索 | 前端 | 預建索引打包成靜態檔，例如使用 MiniSearch |
| 生成 | 家用電腦 Ollama，經 Cloudflare Tunnel 連線 | 可拔除 |

降級規則：

- 頁面載入時先打 health check，在介面上標示目前是完整版或降級版
- 生成 API 遇到任何非 2xx 回應、網路錯誤或逾時 → 切換到降級模式
- 降級時：顯示問診結果 + 相關條文原文 + 轉介資源（只少了生成層）

```js
async function generate(payload) {
  try {
    const res = await fetch(API_URL, {
      method: 'POST',
      body: JSON.stringify(payload),
      signal: AbortSignal.timeout(15000),
    });
    if (!res.ok) throw new Error(res.status); // fetch 不會因 HTTP 錯誤自動 reject
    return { mode: 'full', data: await res.json() };
  } catch {
    return { mode: 'degraded' };
  }
}
```

待評估： Phase 1 先使用前端 BM25 搭配 metadata 過濾（問診樹已經把範圍收得很窄）。之後評估是否在後端加入向量檢索，做成混合檢索（BM25 + 向量）。

## 4. 資料

### 4.1 來源優先順序

1. 全國法規資料庫的開放資料（結構化 XML/JSON，含條號與修正日期）
2. 主管機關網站的公告和說明頁（例如行政院消保處），用 Playwright 抓取
3. 以上都無法取得時 → 告知使用者手動複製原文

### 4.2 處理規則

- 原文入庫，不經過模型改寫或摘要。
- 每筆資料必須附上：`source_url`、`fetched_at`、`law_name`、`article_no`、`amended_at`
  - **修訂（Phase 1）**：不再要求 `amended_at`（逐條修正日）。改以出處可追溯性為核心：來源類型、發布單位、`source_url`、`fetched_at`、開放資料 `UpdateDate`、原始檔案與其 SHA-256。法規層級的日期若來源有附帶則保留，不做額外處理。見 ADR 0006。
- 以條為切分單位，不依 token 數切塊
  - **修訂（Phase 1）**：行業別公告是「點」不是「條」，因此切分單位為「條」或「點」（另有前言、附表列），共用同一個 unit 結構。見 ADR 0002。
- 保留階層 metadata：法規 → 章節 → 條
- 解析「準用第〇條」、「依前條規定」等交叉引用，建立引用關係表，檢索時一併帶出被引用的條文
- 版本快照基準日：2026-11-01（修訂（Phase 0）：已定案，見 ADR 0005；實際時間戳以開放資料 UpdateDate 與 fetched_at 為準）
- 抓取時限制請求頻率，遵守網站使用條款

### 4.3 條文資料結構

**修訂（Phase 1）— 實際採用的結構**：所有文件共用一種 unit 記錄（條／點／前言／附表列），輸出為 `data/laws/<doc_id>.json`，另有引用關係表 `data/laws/references.json`。完整欄位說明與範例見 [data/README.md](../data/README.md)。摘要：

```yaml
- id: cpa-019                 # 全域唯一；點：gym-must-010
  doc_id: cpa
  law_name: 消費者保護法
  unit: article               # article | point | preamble | table_row
  no: "19"
  no_label: 第 19 條
  part: ""                    # 點的所屬部分：應記載事項 / 不得記載事項 / 前言 / 附表
  chapter: 第 二 章 消費者權益
  section: 第 三 節 特種交易
  hierarchy: [{level: 章, label: ...}, {level: 節, label: ...}]
  status: active              # active | deleted
  text: (官方原文)
  references: [cpa-018]       # 已解析的引用目標 id
  external_references: []     # 範圍外法規的引用
  unresolved_references: []   # 無法確定的引用（不猜）
  source_url: ...
  fetched_at: ...
```

文件層級（`doc.source`）另有：`source_type`、`publisher`、`open_data_update_date`、`raw_file`、`raw_sha256`、授權與出處聲明。

## 5. 問診樹

### 5.1 節點定義（寫成資料，不寫死在程式中）

```yaml
- id: online.return
  label: 網購退貨
  type: query            # query | process | out_of_scope
  law_scope: [消費者保護法, 通訊交易解除權合理例外情事適用準則]
  slots: [購買管道, 收貨日期, 商品類型, 是否拆封]
```

### 5.2 規則

- 深度控制在 2～3 層；補充事實用葉節點的表單一次問完
- 只問會讓答案分岔的欄位；使用者已經提供的資訊不要重複問
- 回答類型有三種：規則型（法律怎麼規定）、例外型（哪些情況不適用）、流程型（我該怎麼做）
- 樹本身就是範圍宣告：樹上有的分支 = 支援的範圍

### 5.3 候選葉節點（待確認）

- 網購退貨（規則型）
- 不能退貨的例外商品（例外型）
- 禮券（規則型）
- 健身房解約（規則型）
- 消費申訴流程（流程型）

## 6. 轉介資源表

不放進 RAG，由人工維護，系統只查表。

只收公部門或公益機構，不收私人事務所。

```yaml
- id: consumer_hotline
  name: 全國消費者服務專線
  phone: "1950"
  url: ...
  applies_to: [consumer.*, out_of_scope.consumer]
  source: (官方網址)
  last_verified: (日期)
```

候選項目：1950 消費者服務專線、各縣市消保官、法律扶助基金會、地方法院訴訟輔導、律師公會免費法律諮詢。所有資料都要附上來源與驗證日期，並定期重新驗證。

## 7. 評測集（架構完成後再建立，此處只定原則）

以葉節點為單位分組。

題目來源：主管機關 FAQ 優先，之後再加入新聞、消保處的爭議案例、判決書中的事實描述

- 判決書只取「事實」當題目，判決見解不一定能作為標準答案
- 新聞要注意報導當時的法規版本

量測項目：

- 檢索：應該撈到的條文有沒有撈到
- 引用：回答引用的條號是否正確
- 行為：該回答／該追問／該拒答／該轉介的，有沒有做對

另外準備範圍外題組（測試辨識與轉介）和跨範圍題組。

評測題目與語料完全隔離：不能放進 DB，也不能寫進 prompt。

## 8. README 必須包含

- 系統定位與免責說明（法規資訊查詢，非法律意見）

- 設計取捨：見 2.3 節
- 已知限制：
  - 本系統不處理緊急狀況，正式產品需另行設計安全機制

- Demo 影片（避免面試時後端離線）
