# 0002 以「條」為切分單位，原文入庫不改寫

- 狀態：已採納（Phase 1 補充「條／點並存」）
- 日期：2026-10-31

## 背景

法規是高度結構化文本，每個回答必須能回溯到官方條號與原文。一般 RAG 常以固定 token 數切塊，但這會切斷條文、混合不同條，破壞可追溯性。全國法規資料庫的開放資料本身即以條為單位提供（含條號、章節標記）。

## 考慮過的選項

1. 固定 token 數切塊（含 overlap）。
2. 以「條」為最小單位，保留 法規 → 章節 → 條 的階層 metadata。
3. 由模型摘要或改寫條文後再入庫。

## 決定

採選項 2，並且原文原樣入庫，不經過模型改寫或摘要。

- 每筆資料附 `source_url`、`fetched_at`、`law_name`、`article_no`、`amended_at`。
- 解析「準用第〇條」「依前條規定」等交叉引用，建立引用關係表，檢索時一併帶出被引用條文。
- 條文很長時（例如含多款項）仍維持一條一筆，顯示時可摺疊，不拆開。

## 代價/後果

- 條文長度不均，個別條文可能很長，對 BM25 的長度正規化有影響，需在 Phase 2 觀察。
- 非條文型資料（定型化契約「應記載及不得記載事項」是「點」而非「條」）需定義等價切分單位，已於 Phase 1 定案，見下節。
- 好處是引用 100% 可驗證，評測的「引用正確率」可直接以條號比對。

## Phase 1 補充：條與點並存的切分方式

行業別公告（禮券、健身中心）的結構是「壹、前言／貳、應記載事項／參、不得記載事項」，下設以「一、二、三」編號的「點」，點內再有（一）（二）款與 1. 2. 目。法規（消保法等）則是「編／章／節／條」。為了讓前端用同一個索引、同一套過濾，所有文件共用一種 **unit** 記錄：

| unit | 對應 | 切分規則 |
|---|---|---|
| `article` | 法規的「條」 | 一條一筆；之N條（如第 19-1 條）各自一筆；已刪除的條保留並標 `status: deleted`，以維持「前條」的語意 |
| `point` | 公告的「點」 | 一點一筆，款、目、續行段落都留在該點的 `text` 內，不拆開（與「條不拆款項」相同的原則） |
| `preamble` | 公告的「前言」 | 整段一筆（只有禮券公告有） |
| `table_row` | 公告附表的一列 | 禮券公告的「主管機關及適用範圍」附表，一列一筆 |

統一的 metadata：

- `id`：全域唯一且穩定，條為 `cpa-019`、`cpa-019-1`，點為 `gym-must-010`、`gift-mustnot-003`。
- `unit`、`no`、`no_label`：單位種類、編號、顯示用標籤。
- 階層：法規的 `chapter`／`section`／`hierarchy`（法規 → 章 → 節 → 條）；公告的 `part`（應記載事項／不得記載事項／前言／附表）→ 點。兩者都放進 `path`，前端可用 `doc_id`、`unit`、`part`、`chapter`、`section` 做 metadata 過濾。
- 點引用「第十點」時，預設指向同一個 `part`（兩份公告都是在應記載事項中自我引用），其他情形標為 `ambiguous`，不猜。

新增的代價：點的長度差異比條更大（例如健身中心第十點含多層款目，約 700 字），Phase 2 評估 BM25 時需觀察是否要對長點加權或拆分顯示（顯示拆分不影響入庫單位）。
