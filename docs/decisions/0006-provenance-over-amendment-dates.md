# 0006 不追逐條文修正日，以出處可追溯性為核心

- 狀態：已採納
- 日期：2026-10-31

## 背景

規格 4.2 原要求每筆資料附 `amended_at`（修正日期）。Phase 0 核對發現：

- 全國法規資料庫開放資料只提供**法規層級**的異動日期（`LawModifiedDate`），沒有逐條修正日；逐條日期只能自 `LawHistories` 沿革文字解析（需處理「修正第 2、8、11-1、13…條」這類寫法與歷次修正），成本高、容易出錯。
- 行業別公告（禮券、健身中心）的沿革是整份公告的令號清單，同樣沒有逐點日期。
- 專案真正需要的是讓使用者與面試官確認「這段文字確實來自政府機關、取自哪個頁面、什麼時候取得」，而不是條文的歷史演變。

## 考慮過的選項

1. 解析沿革，建立逐條 `amended_at`。
2. 只保存法規層級日期，作為每筆資料的 `amended_at`。這會讓人誤以為整部法規都在該日修正，語意不正確。
3. 不追逐修正日；以出處欄位承擔可追溯性。法規層級日期若來源有提供，原樣保留但不處理。

## 決定

採選項 3。`amended_at` 不再是必填欄位，也不產生。每部文件記錄（`doc.source`）：

- `source_type`：`open_data`（全國法規資料庫 Open API）或 `ey_webpage`（行政院網站）
- `publisher`、`source_url`（官方頁面）、`file_url` / `api_url`（實際下載位置）
- `fetched_at`：下載時間
- `open_data_update_date`：開放資料檔自己的 `UpdateDate`（內容「截至何時」的權威說法）
- `raw_file` 與 `raw_sha256`：原始檔案原樣保存在 `data/raw/`，並記錄雜湊
- `license` 與 `attribution`：授權條款與出處聲明（`NOTICE.md`）

每筆 unit 另有 `source_url`、`fetched_at`。文件層級來源本身附帶的日期（如 `law_modified_date`、公告令號）原樣保留，供顯示參考，不參與任何邏輯。

驗證腳本（`scripts/validate.py`）會檢查原始檔雜湊、條文與原始檔逐字相符，以此證明「資料來自該來源且未被改寫」。

## 代價/後果

- 無法回答「這一條何時修正」，也無法依修正日篩選。這不在專案目標內。
- 版本新舊以快照日（ADR 0005）與 `open_data_update_date` 表達，而不是逐條時間。
- 省下沿革解析的工作量與出錯風險；若日後需要，原始沿革文字仍在 `data/raw/moj/*.json` 的 `LawHistories`，可以補做而不必重抓。
