# 0007 中文檢索使用字元 bigram 為主、低權重 unigram 為輔的 tokenizer

- 狀態：已採納
- 日期：2026-10-31

## 背景

前端以 MiniSearch（BM25）檢索條文（ADR 0004）。中文沒有空白分詞，MiniSearch 預設 tokenizer 會把整段中文當成一個詞，無法使用。語料是 231 筆法規原文，查詢則是問診樹作者寫的詞，加上「其他」分支裡使用者的口語輸入。

## 考慮過的選項

1. **中文斷詞套件**（如 jieba 的 JS 移植版、Intl.Segmenter）：詞典要打包進靜態檔，法律用語（「通訊交易」「定型化契約」）不一定在詞典內，斷詞錯誤會直接造成漏檢；Intl.Segmenter 在各瀏覽器的詞典也不一致，結果不可重現。
2. **字元 bigram**：不需詞典，建置與查詢行為完全確定，法律用語多為 2～4 字，bigram 能直接命中。缺點是口語與條文用字不同時（「退貨」對「退回商品」）沒有共同 bigram。
3. **bigram + 全部 unigram**：補回口語的召回，但單字（「退」「契」）會讓不相干的條文排前面。
4. **bigram 主欄位 + unigram 低權重欄位**（採用）：同一份文字同時進兩個欄位，bigram 欄位權重 1、unigram 欄位權重 0.25（標題為其 2 倍），unigram 排除「之、或、及、應、得、第、一…」等虛字與數字字。命中一組完整的 bigram 仍明顯勝過只共享單字。

## 決定

採選項 4。實作在 `web/src/lib/tokenizer.js`（切字）與 `web/src/lib/engine.js`（欄位與權重）。同時：

- 全形先 NFKC 正規化；英數字當作整個詞；標點與空白會截斷 bigram，不跨句產生假詞。
- 查詢端 token 去重，文件端不去重（保留詞頻）。
- **先過濾、再 BM25**：節點的 `law_scope` 先以 metadata（`doc`、`part`、`section`、`chapter`、`ids`）篩出單位，再只對這些單位建立（並快取）一個 MiniSearch 索引，因此 IDF 反映的是縮小後的範圍，而不是全庫。`status: deleted` 的單位不會進入任何索引。
- 引用展開不經過索引，直接查 `references.json`，所以已刪除的條文仍能以「已刪除」標示被帶出。

## 數字（開發用的煙霧測試，不是 Phase 5 評測集）

用 20 句口語查詢在全庫檢索（每句有 1～2 個預期條文），比較 unigram 權重：

| unigram 權重 | MRR | hit@5 | hit@10 |
|---|---|---|---|
| 0（純 bigram） | 0.511 | 12/20 | 12/20 |
| 0.1 | 0.476 | 12/20 | 15/20 |
| 0.25（採用） | 0.468 | 12/20 | 14/20 |
| 0.5 | 0.466 | 12/20 | 14/20 |
| 1 | 0.466 | 11/20 | 15/20 |

樣本只有 20 句，差距不大，不宜當成統計結論；它只支持兩件事：unigram 把 hit@10 從 12 拉到 14～15，代價是前幾名多一些雜訊（MRR 下降約 0.04）。因為問診樹已把範圍縮小，我們更看重「撈得到」而不是「排第一」，所以接受這個代價。權重取中間值 0.25，沒有針對這 20 句再細調。

## 代價 / 後續

- 口語與條文用字完全不同時（「鑑賞期」「內衣褲」「倒閉」「電商」）仍撈不到或排很後面；阿拉伯數字與中文數字（「7天」對「七日」）也不互通。這是詞彙落差，不是 tokenizer 能解的，是 Phase 5 評測與是否加向量檢索（spec 10）的主要依據。問診樹的 `query` 欄位由作者用條文用語撰寫，等於人工做了一次詞彙對映，詳見 ADR 0008。
- 小範圍（例如 6 個單位）的 BM25 一定會回傳填充用的低相關條文（如「本準則自…施行」），顯示端以 `top_k` 截斷，但不做相關度門檻（分數跨查詢不可比）。
